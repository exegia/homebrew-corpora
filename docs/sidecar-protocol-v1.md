# Corpora CLI sidecar protocol, version 1

The sidecar runs local work for the Corpora desktop app. It owns process execution;
the converter and Context-Fabric remain the sources of truth for their output.
This protocol implements an initial EPUB-to-Text-Fabric job. The EPUB validator
and exporter remain separate `corpora-core` executables and are not currently
bundled with the `corpora-cli` package or Homebrew formula. The sidecar advertises
`epub_to_tf` only when both tools and the platform's atomic no-replace publish
operation are available. Install/configure `corpora-epub-check` and `epub-to-tf`
on `PATH`, or set `CORPORA_EPUB_CHECK_BIN` and `CORPORA_EPUB_TO_TF_BIN` to their
absolute executable paths. Without them, `ready.capabilities` is empty and a
start request returns `runtime_unavailable`.

## Human-facing command

The command is `corpora convert-epub INPUT --output OUTPUT`. It invokes
the same job implementation as the sidecar, writes human-readable progress and
diagnostics to standard error, and writes the completed bundle path to standard
output only on success. It exits 0 for success, 1 for a rejected or failed job,
2 for invalid arguments or unavailable capability, and 130 for cancellation.
The existing `corpora convert` command is unchanged. This EPUB bundle path is
separate from the released `.corpus` conversion path.

## Transport

Start `corpora sidecar --protocol 1` as a child process. Standard input and
standard output carry UTF-8 newline-delimited JSON objects, one per line. The
sidecar sends a `ready` event first. Standard output contains protocol messages
only; diagnostic logs go to standard error and must not contain source text,
credentials, or full local paths. There is no network listener.

Each message includes `protocol: 1` and a `type`. Requests include an opaque,
unique `request_id` (1–128 ASCII letters, digits, `_` or `-`); the reply echoes
it. A client must not reuse an ID during a process lifetime. Unknown fields and
unknown message types are errors in both directions in version 1. Frames are limited to 1 MiB,
including the newline. Inputs are absolute local paths; they are never sent to a
remote service by the sidecar. Relative paths, NUL, and non-local URI schemes are
invalid. A sidecar must not accept a secret in a request or output it in an event.

On malformed JSON, oversized frames, or incompatible protocol versions, emit a
`protocol_error` when possible and close the process; do not attempt to continue
after losing frame boundaries. Request validation errors with a valid, unique
request ID return an `error` response and leave the process running. A missing,
invalid, or repeated request ID is a protocol error and closes the connection.

## Messages

The start command uses a new job ID generated by the sidecar. The output directory
must not exist. Before acknowledging a job, reserve its destination and create a
private staging directory. The acknowledgement includes its absolute path so the
app can identify possible leftovers after a crash. Accepted means the job was
admitted, not that it completed. If the process exits before acknowledging a
start request, its outcome and staging path are unknown; the app must not assume
that no work started or automatically retry into the same destination.

```json
{"protocol":1,"type":"ready","capabilities":["epub_to_tf"]}
{"protocol":1,"type":"start","request_id":"req-1","operation":"epub_to_tf","input":{"path":"/Users/example/book.epub"},"output":{"path":"/Users/example/book-tf"},"options":{"repair":false}}
{"protocol":1,"type":"accepted","request_id":"req-1","job_id":"job-1","staging_path":"/Users/example/.book-tf-job-1"}
{"protocol":1,"type":"progress","job_id":"job-1","phase":"validating","message":"Checking the EPUB"}
{"protocol":1,"type":"diagnostic","job_id":"job-1","severity":"warning","code":"EXAMPLE","message":"Review this source","location":{"member":"chapter.xhtml","line":12,"column":3}}
{"protocol":1,"type":"progress","job_id":"job-1","phase":"converting","message":"Writing Text-Fabric"}
{"protocol":1,"type":"finished","job_id":"job-1","outcome":"succeeded","outputs":[{"kind":"tf_bundle","path":"/Users/example/book-tf"}]}
```

Only advertise operations whose required runtime is actually available. The
initial operation takes an unencrypted EPUB, a fresh output directory, and an
optional `repair` boolean defaulting to `false`. Repair may only use the core
converter's audited policy. Unsupported format, unavailable converter, unsafe
input, or an existing output directory must fail explicitly. The converter
retains the original EPUB and provenance in the bundle when it succeeds.

`progress` is a phase transition or other truthful update. `phase` is one of
`validating`, `converting`, `finalizing`. It has no percentage unless the
underlying worker reports a measurable fraction; this version makes no promise
of numerical progress. `diagnostic` fields `severity` (`info`, `warning`,
`error`), `code`, and `message` are required; `location` is optional, with
optional archive `member`, one-based `line`, and one-based `column`. Diagnostics
are suggestions or findings, not permission to modify the source. Large reports
must be emitted as separate bounded messages, not truncated silently. If one
diagnostic cannot fit in a frame, fail the job with `diagnostic_too_large`.

## Cancellation and terminal results

```json
{"protocol":1,"type":"cancel","request_id":"req-2","job_id":"job-1"}
{"protocol":1,"type":"cancel_ack","request_id":"req-2","job_id":"job-1","status":"requested"}
{"protocol":1,"type":"finished","job_id":"job-1","outcome":"cancelled","outputs":[]}
```

The sidecar owns the job lifecycle and emits **exactly one** `finished` event per
accepted job while its process is alive. Outcomes are `succeeded`, `failed`, or
`cancelled`. Only a successful job may expose an output as a completed bundle;
failed and cancelled events have empty `outputs` and include a bounded `error`
object for failures (`code`, `message`). A cancelled job has no error object.
When cancellation is requested, `cancel_ack` says `requested`; it does not claim
the worker has stopped. A job may still succeed or fail if it finishes first.
Atomic publication is the commit point: once publication succeeds the terminal
outcome must be `succeeded`, even if cancellation arrives concurrently.
Cancelling an already finished or unknown job returns `error` with code
`job_not_running`. A repeated cancellation while stopping is acknowledged as
`requested`. A job does not emit progress or diagnostics after `finished`.

```json
{"protocol":1,"type":"error","request_id":"req-3","code":"job_not_running","message":"The job is not running"}
{"protocol":1,"type":"finished","job_id":"job-2","outcome":"failed","outputs":[],"error":{"code":"invalid_epub","message":"EPUB validation failed"}}
{"protocol":1,"type":"protocol_error","code":"invalid_frame","message":"Invalid protocol frame"}
```

Stop and reap the worker and its descendants before emitting a terminal event;
no worker may write job output after `finished`. Write to a private sibling staging
directory, then atomically publish it using a no-replace operation. Fail closed
if the platform cannot guarantee atomic no-replace; a check followed by a normal
rename is insufficient. On failure or cancellation, remove only staging files
created by that job; never delete the input or a pre-existing output. If cleanup
cannot be confirmed, emit `failed` with error code `cleanup_incomplete` and an
absolute `error.staging_path` identifying the job-owned staging directory.
Reserve destinations across processes, accounting for resolved parents, aliases,
and symlinks. Reject output equal to or containing the input or staging directory;
protect parent traversal against symlink changes. Never delete a path merely
because its name matches a staging convention. Abrupt sidecar
termination can leave staging files: the app must report the outcome as unknown
and must not automatically delete or overwrite them.

## Ordering and failures

`accepted` precedes all events for that job. Requests may be interleaved and
responses can arrive out of order, so match responses by `request_id` and job
events by `job_id`. There is no persistence or reconnect in v1. If the sidecar
exits or the pipe closes before `finished`, the app reports an unknown result,
retains any user source, and offers a fresh job only after checking the requested
output path and the `staging_path` from `accepted`. EOF on stdin requests shutdown: stop accepting work, request
cancellation of active jobs, flush terminal events if possible, then exit.
Diagnostics and failures must be sanitized; no shell is used to construct
commands, and the sidecar must not follow archive paths outside the staging area.

The implementation has executable protocol tests with stand-in core tools. A
release still requires packaging the actual core runtime or documenting how the
desktop installer provides it; fake-tool tests do not establish that a packaged
installation can perform a real conversion.
